# Firmware updates — implementation status and plan

**There is no production update flow yet.** CI emits UF2 and HEX files for the
nRF52840 DK bring-up application. The repository does not build a NotchDeck
bootloader, OTA package or STM32 panel image. Rev E/F needs two separately programmed
MCUs; the existing nRF direct-GPIO application does not operate its panel.

## Current build outputs

See the [firmware guide](../firmware/README.md) for NCS v3.3.0 workspace setup.
From the repository root:

```sh
make -C firmware build
make -C firmware uf2
make -C firmware release
```

| Output | Meaning |
|---|---|
| `firmware/build/firmware/zephyr/zephyr.uf2` | Application UF2 generated by NCS sysbuild with `CONFIG_BUILD_OUTPUT_UF2=y` |
| `firmware/build/firmware/zephyr/zephyr.hex` | Application HEX for the selected build target |
| `firmware/dist/notchdeck-one-vX.Y.Z.{uf2,hex}` | Versioned copies made by `make release` |
| CI `notchdeck-one-firmware` | Default DK build, named `notchdeck-one.uf2` and `.hex`; not a Rev E release |

`VERSION` controls Zephyr's application version and the release filenames.
The BLE DIS revision in `prj.conf` is maintained separately. No target currently
signs images, creates an OTA ZIP or bundles a bootloader. A valid UF2 container
does not establish that its flash addresses match a future production bootloader.

## Main-board user-update plan

The proposed primary experience is USB drag-and-drop: enter a UF2 bootloader,
mount a drive, copy the matching application image, then reboot. An Adafruit
nRF52 bootloader port is a candidate; MCUboot with a suitable update transport
is another option if signed images/recovery slots are required. Neither is
integrated or validated for this board.

The current `dfu.c` writes GPREGRET `0x57` and resets, and `main.c` checks the
Select+Start mask at startup. That is only an entry request for a compatible
bootloader. Double-tap Reset behavior belongs to the bootloader. Rev E must first
implement and verify its local/panel button mapping; an ordinary DK application
build does not create a `NOTCHDECK` USB drive.

Before documenting a user procedure, choose and test the bootloader, board port,
flash partitions/application address, reset behavior and USB identity. Verify a
complete SWD installation, repeated updates, interrupted updates and recovery.
Choose signing and authorization behavior for each enabled update transport.
UF2 is a container format, not itself an authentication policy. BLE OTA remains
future work; HOGP support alone does not provide it.

## Programming access on both boards

| MCU | Access | Signals |
|---|---|---|
| Logic E73 nRF52840 | J3 keyed 10-pin SWD header or bare J4 TC2030 | SWDIO E73 pad37, SWDCLK pad39, reset pad26/P0.18, 3V3 reference, GND |
| Panel STM32G030 | Bare J2 TC2030 | 1=3V3, 2=SWDIO, 3=NRST, 4=SWCLK, 5=GND, 6=NC |

Use one main-board debug connection at a time, observe pin 1 and the target's
3.3V reference, and establish the power/probe setup before flashing. The nRF
requires P0.18 reset configured in UICR and RC LFCLK with the current hardware.
The STM32 must retain SWD and the correct user-flash boot option bytes; see the
[panel pin plan](../hardware/notchdeck-buttons/README.md#mcu-pin-plan).

SWD is the planned development, factory programming and recovery interface.
Recovery depends on the device protection/configuration state and may require
an erase. The panel has no USB connector and no implemented I²C bootloader.
A future coordinated update feature must define panel image compatibility and
recovery before assuming the main USB update also updates the panel.

The [net plan](../hardware/NETPLAN.md) records captured programming/reset wiring.
Both boards remain unrouted; bootloader behavior and hardware access still need
validation on assembled boards.
